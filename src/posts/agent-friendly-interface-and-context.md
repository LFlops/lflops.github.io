# 传统项目 Agent 化：通用 Agent 够强，缺的是 Agent 友好的接口和上下文

> 不是造 Agent，是让系统可被 Agent 操作，并给它足够的上下文。

---

先说一个有点丧的事实：正版动画的黄金时代过去了。

自打《无职转生》那场风波之后，B 站买番越来越少，删减、延期、下架成了常态。想看完整的番，很多人又回到了两条老路：在 B 站看 UP 主上传的资源，或者自己去找 BT。

这篇文章想聊的不是看番，而是一个更工程的问题：通用 Agent 已经够强了，为什么还是接不进这个系统？

记录断了之后，我回到了 Bangumi，靠“打格子”记录观看时间和进度。Android 上有 Animeko，搜索、观看、记录同步能在一个 App 里完成；iOS 没这个命，受苹果的限制，BT + Infuse 是比较现实的方案。Infuse 负责播，Trakt 负责记，Bangumi 负责最终归档。中间没有直达车，得有人把 Trakt 的记录清洗、匹配、写进 Bangumi。这是我上半年做的功能（[#99](https://github.com/SanaeMio/Bangumi-syncer/pull/99)）。

功能能跑，但不够好。现有清洗规则依赖播放器输入的标题，按我的估计，80% 的场景没问题，剩下 20% 的边缘场景——季号偏移、别名、typo、剧场版、同名不同年份——还是会匹配失败，最后要人工介入。

这是 LLM 匹配的原点。

MCP 是另一个原点：项目的配置项越来越多，每次界面重构，用户的学习成本就再涨一轮。

一个是如何让外部 Agent 操作 BS，一个是如何补 BS 到 Bangumi 的那段断点。

---

## 1. 通用 Agent 够强，但缺 Agent 友好的接口和上下文

### 1.1 它强在能力，弱在上下文

Claude Code、Codex 这类通用 Agent 已经够强了。再造一个通用 Agent，对我这个项目没有意义。

我不是说它什么都能做。我是说，在“工具明确、目标明确”的垂直任务里，它已经够强了。

它强在能调工具、能拆步骤、能从错误里恢复。

它缺的是上下文。

这里的上下文，不是聊天记录，是这次任务的数据来源、字段语义、领域规则、目标、失败策略和权限边界。

你可以把 API key 和浏览器都给 Claude Code，让它同步一集观看记录。它会先问你：

- 数据从 Plex、Emby、Jellyfin、Trakt 还是 fongmi 来？
- 标题里的字幕组、分辨率、季号、集号，怎么拆？
- 这一集对应 Bangumi 的哪个 subject、哪个 episode？
- 匹配失败时，是重试、放弃，还是进候选池？
- 写进度的时候，用哪个账号？

你把这些都告诉它，它能做。下次换一部番，你又要重新告诉它一遍。

正因为它什么都能做，没有上下文时，它面对的选择太多，反而什么都做不了。

### 1.2 不是没有接口，是接口不是给 Agent 用的

Bangumi 有 Web UI，有 API key，也有 OAuth。

Agent 不是不能用：给它 API key，它能调；给它浏览器，它能点。问题是，这两种方式通常都要人值守。

UI 是给人看的，API key 是给代码调的。Agent 夹在中间：它能操作，但它不知道该操作什么，也不知道什么时候该停。

所以缺的不是接口，是 Agent 友好的接口。

MCP 不是补一个不存在的接口，是把已有的能力重新封装成 Agent 能用的形状。

### 1.3 MCP 补接口，领域 Agent 补上下文

MCP 让它能做事。

领域 Agent 让它知道，在这件事里该做什么、不该做什么。

我说的领域 Agent，不是另一个通用 Agent，是一个只做匹配、只拿匹配工具、只写候选池的受限循环。

它不负责“什么都能做”，它只负责把一集动画匹配到正确的 subject/episode，然后停下来等人确认。

先接口，后断点。上下文不够，接口再多也没用。

---

## 2. 向外：MCP 补接口

### 2.1 最常见的报障

最常见的报障是“同步没生效”。

以前：先确认媒体库 webhook，再翻配置页，再找日志文件，再改配置、复读验证。每一步都要知道一个配置键，或者一个页面在哪里。

MCP：外部 Agent 调 `get_logs` 看错误，调 `get_current_config` 看配置，给出根因；需要改配置时，先给变更计划，用户确认后调 `update_config`，再复读验证。

这个需求最早记在 [#245](https://github.com/SanaeMio/Bangumi-syncer/issues/245) 里：允许外部 Agent 通过 MCP 配置 Bangumi-syncer。后来拆成 #257–#262 落地。

### 2.2 不是把 Web API 包一层

最直接的做法，是把 Web API 一套一套包成 MCP 工具。

但这不是第一性原理。

第一性原理是：人能在 BS 里做什么？

- 人能看日志；
- 人能看配置；
- 人能改配置。

Agent 要的是这三个能力，不是三个 endpoint。

| 人能做什么 | Web 入口 | MCP 工具 |
|---|---|---|
| 看日志 | 日志页 | `get_logs` |
| 看配置 | 配置页 | `get_current_config` |
| 改配置 | 配置页 | `update_config` |

实现上，MCP 也不是 HTTP 客户端。`get_logs` 直接复用日志读取，`get_current_config` / `update_config` 直接调 `ConfigManager`。

传输不是一套，能力是一套。

人能通过这些接口操作 BS，Agent 也可以通过 MCP 操作 BS。这不是“把 API 暴露出去”，是“把人能做的事，交给 Agent 也能做”。

首批只做三个，是 MVP 范围：先把“看日志 → 看配置 → 改配置 → 复读”跑通。以后要不要扩，是另一个决策。

配置和日志接口的鉴权本来就统一，都走 `get_current_user_flexible`。MCP 是另一个入口，走 OAuth scope。不是每个 API 一套鉴权。

### 2.3 三条硬边界

| 工具 | 人能做什么 | 需要的权限 |
|---|---|---|
| `get_logs` | 看日志 | `read` |
| `get_current_config` | 看配置 | `read` |
| `update_config` | 改配置 | `write` |

三条硬边界：

- 登录三键禁写：`auth.enabled`、`auth.secret_key`、`auth.password`；
- `[bangumi]` 段只读；
- 敏感字段读取时掩码。

这些是服务端直接拒绝，不是 prompt 里的提醒。

但要注意：**“计划 → 用户确认 → 执行 → 复读验证”不在这三条里。** 它是 Skill 层的软约束，服务端目前没有强制。

### 2.4 Skill 与可恢复

Skill 把“部署 → 配置 → 排障”写成剧本：计划 → 用户确认 → 执行 → 复读验证。

但 Skill 是软约束。它依赖模型的指令遵循性，不同客户端、不同模型可能不完全照做。

真正的可恢复设计是另一件事：**MCP 不能修改登录通道三键。** 即使 MCP 授权配坏了，用户还能从 Web 登录进去修。

OAuth 的地址一致性是另一个问题。`mcp_base_url` 用来生成 issuer 和 metadata；如果客户端访问的地址和它不一致，OAuth 发现会对不上。配置页的“一键填入”只是把当前浏览器的 origin 填进 `mcp_base_url`，而且只在输入框为空时填。它降低配错概率，但不是可恢复机制。

`mcp_base_url` 和 `auth.enabled` 是启动期配置，改完要重启；普通配置通过 `set_config` 写回内存并触发变更回调，改完即生效。

当前还有一个缺口：`update_config` 没有服务端的两阶段确认。“先给计划、等用户确认”只写在 Skill 里。

### 2.5 复盘

向外这条路的收益不是自动化，是认知成本：用户不需要记住每个配置键和日志位置。

代价是权限、协议、审计都要补。

MCP 能查日志、改配置，但它不能替你把一集动画匹配到正确的 subject/episode。

这不是接口问题，是上下文问题。

## 3. 向内：领域 Agent 补上下文

### 3.1 一条日志

issue [#182](https://github.com/SanaeMio/Bangumi-syncer/issues/182) 里有一条日志：

> 通过 bangumi-data 匹配到番剧 ID: 325585, 匹配标题: 无职转生 ～在异世界认真地活下去～ 第二季, 日期匹配: True

请求是第三季，命中是第二季。标题对，日期对，季不对。

这不是哪一行代码写错了。规则只能判断“这个候选像不像”，判断不了“是不是只有一个像”。

### 3.2 匹配是流水线

很多人以为匹配是“拿标题去 Bangumi 搜一下”。实际代码里，它是一串步骤：

1. **归一化**：去发布组、分辨率、编码、括号噪声。
2. **本地映射/数据**：自定义映射、bangumi-data、Archive 短路。
3. **在线搜索**：搜索、候选打分、季/媒体类型/关联条目改选。
4. **裁决层**：跨源加权、margin 门控，默认关闭。
5. **集数解析**：季/集 → Bangumi 剧集 ID，处理偏移、SP、剧场版。

每一步都带着自己的假设：

- 归一化假设“标题里的噪声可以去掉”；
- bangumi-data 假设“本地数据至少收录了目标条目”；
- Archive 假设“第一个候选就是对的”；
- 集数解析假设“episode 就是 sort”。

任何一个假设不成立，后面就会错。

这条链不是一个人写的。@musnow 做了管线化重构和季号判决，@wan0ge 修了大量 Trakt、季号、Archive 的边界，@SanaeMio 修了最早的续集链和无职 S3。

### 3.3 为什么规则补不完

再举两个 issue。

[#269](https://github.com/SanaeMio/Bangumi-syncer/issues/269) 里，同一部《正相反的你与我》：

- 季 2、集 1，发布日期 2026-07-04；
- 季 1、集 13，发布日期也是 2026-07-04。

结果 S02E01 命中第一季第 1 集，S01E13 命中第二季第 13 集。标题没错，季的语义错了。

[#97](https://github.com/SanaeMio/Bangumi-syncer/issues/97) 里，《生徒会役員共*》的日志只有一句：

> subject_id='85204' item.season=2 item.episode=13, 不存在或集数过多，跳过

episode、sort、总集数、SP 编号，四个概念里有一个对不上，整条同步就失败。

三个案例，三种漏法：季划分、数据缺失、集数解析。

漏掉的不是“规则数量”，是“边界类型”：

- **命名不可枚举**：LoliHouse、樱花等字幕组各有规则，中文名、英文名、罗马音混用。
- **季划分不一致**：TMDB、Emby、Trakt、Bangumi 各切各的。
- **本地数据不完整**：bangumi-data / Archive 只收录了同名异条目。
- **集数解析**：episode、sort、总集数、SP、剧场版是四个概念。

代码注释里记录过，Archive 短路 76 条盲信命中里 10 条标错。

你可以再写十条规则。但下个字幕组、下一个季划分、下一个字段缺失，还是会漏。

规则覆盖的是已知边界，LLM 处理的是未知边界。

### 3.4 LLM 补在哪

我们没有让 LLM 取代规则链。规则匹配还是主路径，LLM 只在规则失手之后启动。

它拿到的工具很少：搜索条目、看条目详情、校验条目类型、看关联条目、提交推荐、明确放弃。调用的是同一套 Bangumi API client，做的是“在候选里做语义判断”，不是“重新实现匹配”。

结果也不直接写库：先进入候选池，人确认后才落映射。

和 maintainer 聊 Agent 怎么设计时，他说了一句：

> 正常的业务不管是不是崩溃后恢复，都不会让 LLM 的结果直接入库，都要人工审核。

所以候选池不是可选项，是这条线的边界。

同步错了，用户可以去 Bangumi 撤销，它不是不可逆的。但错误会被隐藏。S3 被写成 S1，进度看起来是合理的；用户可能几天后才发现。撤销的前提是发现，发现的前提是有人盯着。

候选池的价值，是把错误挡在写库前，而不是事后靠用户撤销。

规则负责确定性，LLM 补不可枚举的长尾，人确认最后一厘米。

---

绕了一圈，问题不是“要不要上 Agent”，而是“哪些能力值得做成工具，给谁用”。

如果你也在做一个传统项目的 Agent 化，可以先问两个问题：

- 人能做的操作，Agent 有没有一个不靠人值守的入口？
- Agent 能做的任务，它有没有足够的领域上下文和写边界？

通用 Agent 够强，缺的是 Agent 友好的接口和上下文。MCP 补接口，领域 Agent 补上下文。

先接口，后断点。
