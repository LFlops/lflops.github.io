# 白盒安全测试在 AI 时代：什么被补上了，什么永远补不上

我做了两年白盒安全测试。不是专职安全工程师——是后端开发，每年抽一个月做集中排查。

第一年 1 个组件、1 个代码仓。第二年变成 10 个组件、3 到 4 个代码仓，总共 36 个微服务。三个人按业务团队归属交叉验证，各自审自己所属团队以外的仓——审自己的代码会有盲区，这个道理不用多解释。

这篇文章不教你"白盒安全测试怎么做"。我想讨论的是：做了两年之后回头看，哪些漏洞 AI 能替你发现，哪些漏洞 AI 和你看同一份代码、一样的视角、一样看不见。以及面对后两类漏洞，真正有效的不是换工具，是换工作流。

## 一、两年白盒，流程跑通了什么

先说流程。每年集中排查的时间有限，而且逐年收紧——业务团队视角里，安全排查是非功能性需求，投入的人力每年都在降。人力一直不富裕，两年走的都是增量的路子：**找到去年排查的版本，git diff 锁定变更范围**。

排查分三层：

1. **安全架构师串讲**。从功能出发，标出高风险业务——堡垒机存用户密码、Runbook 这类 To Developer 业务允许用户执行 shell 和 Python 脚本、页面上有自定义文本框的地方需要验证 XSS 和 CSRF、SQL 注入。这是从"攻击者会盯上什么"倒推排查重点。

2. **增量 diff 排查**。新增接口是第一优先级，有改动的接口第二优先级。不只看接口本身——从 Controller 一路追到 Service 层、Data 层，每一层都要过。

3. **表格跟踪**。所有排查项列在表格里，状态、发现、修复方案逐条记录。不是为了流程好看，是因为排查总量超过一百项之后，人的脑子记不住。

两年跑下来，积累了一份清单：哪些问题反复出现、哪些问题规则明确、哪些问题规则有也没用。我把它们拆成了三层盲区。

## 二、AI 补上了第一层：知识性盲区

第一类问题，规则明确、知识可查。出问题不是因为聪明不够，是因为开发者不知道这条规则存在。

### MD5 做凭据缓存

第一年排查，发现缓存 token 时用 MD5 做 key 哈希。写这个代码的是应届生，不是故意的。但 MD5 参与凭据缓存的后果是：如果缓存 key 被碰撞，用户 A 可能拿到用户 B 的凭据。

修复方案是换 SHA-256。这条规则是明确的——敏感凭据的哈希用 SHA-256 以上，不要用 MD5。应届生不知道，AI 知道。你让 Claude Code 扫这段代码，它不太可能漏。

### 日志打印手机号

发版前的例行排查发现的，不是集中排查期。模块负责通知用户，所以能获取到用户的手机号。日志本应打印用户 ID，但开发直接打印了手机号。

这也是规则问题。日志不打印 PII（个人身份信息）——AI 做代码 review 时识别 `phone`、`mobile`、`idCard` 这些字段出现在 log 语句里，比人快得多。

### ReDoS：正则的定时炸弹

Java 原生正则引擎用的是回溯算法。当表达式里出现 `(\s+)+` 这种嵌套量词时，特定输入会让匹配时间指数级增长，直接打满 CPU。

修复方案没有换掉正则引擎——那样影响面太大。改成了包装原生 regex 的 match 操作，统一加超时熔断，配合测试用例看护，防止后续改动把保护逻辑改掉。

这个漏洞有个特点：**规则极度明确，但人肉扫极易漏**。一百个正则里可能只有一个有问题，人看正则看到第二十个就开始跳跃阅读了。AI 不会。

### SQL 注入：MyBatis 里 `${}` 的代价

业务需要根据条件查询不同表，开发在 MyBatis 中用了 `${}` 做动态表名拼接。应用层做了入参校验——但 if 语句存在空悬问题，也没有用枚举类型限制输入范围。接口入参最终直接进入 `${}`，SQL 注入就此产生。

这也是渗透测试的同学在生产环境发现的。当时拉业务方澄清过 `${}` 的用途，但大家的注意力都在"为什么要查不同表"上，忽略了 service 层校验可以被绕过。

修复做了两层：Controller 层入参改用枚举类型，只允许预定义的表名白名单，从入口就堵死注入可能；Service 层修补了 if 空悬逻辑，确保校验分支不会被绕过。`${}` 没有替换成 `#{}`——业务确实需要动态表名，`#{}` 不支持这个场景。堵住注入不靠换占位符，靠收窄入口。

这个案例也属于第一类——`${}` 和 `#{}` 的区别是明确的安全知识。AI 扫到 `$ {` 后面跟用户输入变量时，和扫到 MD5 一样，不太可能漏。

### TLS 证书校验缺失

内网调用的 TLS 证书没有校验。找安全架构师评估了风险之后，结论是仅打印校验失败的日志，不中断连接——内网环境风险可控。

这个判断需要经验，但"这里缺了证书校验"这件事本身，AI 看代码就能发现。

---

第一类盲区的共同特征：**规则存在、知识可查、不依赖业务上下文**。在 AI 之前，这些要靠资深工程师的肌肉记忆和 code review 的耐心。在 AI 之后，机器替你记、替你扫。

但如果你觉得 AI 能覆盖所有安全排查，接下来两种情况会让你重新认识什么叫"盲区"。

## 三、AI 和人一起瞎的第二层：跨层断裂

这类问题的特点是：**你在后端代码里一行一行看，看不到任何问题。因为漏洞不在代码里，在代码和代码之间的缝隙里。**

### XSS：前端做了转义就安全了吗

页面上有一个文本输入框。用户输入的内容会被后端存储，后续展示给其他用户。前端做了两件事：用户输入时实时转义，提交时再过滤一遍。看起来没问题。

安全工程团队的渗透测试绕过了这道防线。用 Postman 直接调后端 API，输入中包含 `<script>` 标签——后端原样存入数据库。前端刷新页面，注入的脚本被执行。

问题在哪？

后端 Reviewer 看的是后端代码：接收请求、存入数据库。每一步都正常。他知道 XSS 需要防范，但他看到的代码里没有 XSS 风险点——输入来自前端，前端已经处理过了。

前端 Reviewer 看的是前端代码：用户输入后转义、提交前二次校验。他知道 XSS 需要防范，而且他确实防范了——至少对来自用户浏览器的输入做了防护。

没有人看"前端向后端发送了什么"和"后端向前端返回了什么"这两条链路合在一起是否安全。**代码各层独立 review 时都是安全的，安全漏洞在交接面上。**

修复做了两层：前端对所有来自后端的字符串也做转义，不止是用户输入。后端在输出时引入第三方库做 HTML 实体转义。不再依赖"前端会处理"这个假设。

### 最少购买数：防了 DOS，忘了最小值

这个问题是渗透测试的同学在生产环境发现的。

购买 API 的页面上，前端限制了最少购买 50 个。后端对最大值做了校验——这是防入参 DOS 的常规操作。但最小值没有。

用 Postman 直接调 API，传 `quantity=1`，后端照单全收。

后端开发不是粗心。他关注的是"别让攻击者把服务打挂"——所以做了最大值校验。至于最小值为什么是 50，那是产品和前端商量好的，后端从需求里看到的只是"这个接口至少能处理 50 个"。

但 Reviewer 看的是同一份后端代码。他看到的也是"有最大值校验，OK"，没有理由去问"为什么最小值没校验"。**最小值 50 这个约束写在 PRD 里，没写在代码里。白盒测试看不到 PRD。**

修复方案是后端增加了最小值校验。

---

这两类问题的共同点：**漏洞不在单层代码里。它在"前端认为后端会校验"和"后端认为前端已经校验了"的双向假设之间。**

而 AI 遇到这两种情况，和人一样瞎。AI 看后端代码，一切正常。AI 看前端代码，有转义、有校验，也正常。AI 不会主动问"这个接口有没有被绕过前端直接调用的可能"——除非你教它这样问。但那是 AI 的问题吗？你自己做白盒 review 的时候也没问。

## 四、工具升级解决不了的第三层：业务逻辑盲区

如果第二层是"代码在多层之间断裂"，第三层更深入一步：**代码本身逻辑正确、写法规范，但它在真实业务场景下是危险的。这需要你知道这个系统是干什么的。**

### 横向越权：改了别人的工单

SaaS 平台，IAM 鉴权。数据库中多个租户的数据并存——CMDB 里的云资源、工单系统里用户的工单。

用户在页面上看自己的工单，请求带了 token。后端用 token 解析出 domainID（租户标识）。正常的权限校验模式是：先根据工单 ID 查出记录，再用查回记录的 domainID 与 token 中的 domainID 比对——不一致则拒绝。问题在于，这一步比对被漏掉了：查询工单时直接用了 `id = ?`，没有校验工单的 domainID 是否属于当前租户。

你用 curl 改一下 URL 里的工单 ID，就能看到别人的工单内容。

排查是怎么发现的？从新增接口的 Controller 开始，一路向下追到 SQL。安全排查 checklist 上有一条："所有数据查询是否校验了 domainID 与 token 的一致性"。看似简单，但执行起来是这样的：

- 一个 Controller 调用一个 Service
- Service 调用一个 Repository
- Repository 里一条 SQL，WHERE 条件只有 `id = ?`，没有 `domain_id = ?`

只有追到最后一行 SQL，你才能确认横向越权存在。中间每一层代码看起来都正常——参数传递、方法调用、异常处理，都没有问题。**漏洞点不在中间处理逻辑里，在 WHERE 条件的缺失上。**

修复方案是在 Service 层增加显式的 domainID 比对逻辑：先根据 ID 查出记录，再用查回记录的 domainID 与 token 中的 domainID 比对，不一致则拒绝。

### 纵向越权：IAM 下自建权限的那套规则

部分业务在 IAM 的基础上自建了一套权限规则。比如工单系统规定：IAM 用户创建工单后，不能自己审批，必须由同一租户下另一个用户审批。

这是 To Developer 场景下的风险操作——脚本执行、shell 执行——要做一人操作一人复核。自建规则本身没问题，问题在于规则的校验逻辑散落在多个判断分支里，有的入口校验了，有的入口没校验。

Reviewer 在看的时候，除非完整理解这套自建权限体系的全部流向，否则只会看到"这里有个 if 判断"，判断条件看起来和别的地方一样——但其实绕过了。

修复方案是针对缺失校验的入口逐点补上了判断逻辑。

### 越权信息泄露：你不该知道我存在

跨 IAM 租户场景下，用户尝试访问其他租户的资源。后端校验了权限，返回了 `403 Forbidden: 您没有权限操作该资源`。

代码没毛病。但从安全角度看，这条消息告诉攻击者：**这个资源是真实存在的，只是你暂时没权限。** 正确的做法是返回 `404 Not Found`——对于无权访问的资源，它就不应该存在。

这完全不是代码质量问题。开发写了一个语义正确的权限校验逻辑，返回了语义正确的 HTTP 状态码。问题是这个语义在安全语境下本身就是信息泄露。

### 审计日志：看似有，实则缺

审计日志排查下来，问题最多。不是没有审计日志框架——框架有，基于注解做 AOP，自动上报。问题出在人和框架的缝隙里。

**第一种，新增接口没有加注解。** 服务交接后，新维护者不了解审计日志框架，新加接口时没有在方法上标注需要审计。框架不会自动帮你加——它只负责有注解的接口。修复方案：在代码 review checklist 里把"新增接口是否标注审计注解"列为必检项，同时在团队 onboarding 文档中强调审计日志框架的使用规范。

**第二种，加了注解但内容残缺。** 审计日志的六要素——谁、何时、何地、何事、如何、结果。有些使用了 SPEL 表达式或反射来获取审计要素，表达式写错了或者反射目标的字段名改了，审计日志静默失败，不会报错。排查时一条一条找：哪个接口的审计日志有"谁"，缺了"何事"——上百条数据人肉翻。修复方案：通过流程中的黑盒测试逐接口验证审计日志的六要素完整性——拿 token 调接口，再查审计日志，逐个确认"谁、何时、何地、何事、如何、结果"是否齐全。注意部分接口（如 list 类查询）本身就不包含资源名称，六要素中的"何事"天然缺失，这类接口在 checklist 中标记为非适用项。

**第三种，业务逻辑中上报的审计日志，异常时可被跳过。** 有些接口不走 AOP 注解，在业务逻辑代码中手动调用审计日志上报方法。坏处是：如果业务逻辑中途抛异常，上报方法还没来得及执行。比如修改资源时，开发在接口返回前才设置资源 ID 到审计上下文，一旦业务抛出异常，上报的审计日志里资源 ID 是空的——只记录了"谁做了某件事"，没记录"这件事做成了没有"。修复方案：将审计上下文的关键字段（如资源 ID）在操作开始前设置，而非返回前；手动上报的场景用 try-finally 包裹，确保异常路径也能触发审计上报。

**第四种，审计日志记错了 IP。** `X-Forwarded-For` 头会随着请求经过多层代理而累积，格式是 `client, proxy1, proxy2, ...`。从哪个位置取值取决于部署架构——取第一个、取最后一个、还是取倒数第 N 个。部分业务简单粗暴地取了第一个或最后一个，实际情况可能都不是真实 IP。修复方案：增加了一个配置项，根据当前部署环境的代理层级手动配置取倒数第几个 IP。不同网络环境的代理层数不同，不存在一个通用的取值位置，只能按环境各自配置。

---

第三类盲区的共同特征：**问题在业务语义里，不在代码语法里。** AI 和 SAST（Static Application Security Testing，静态应用安全测试）工具看代码，只能判断"有没有校验""有没有注解""有没有 return 404"，但判断不了"校验的语义对不对""404 和 403 的区别在这个业务场景下意味着什么""审计日志里记的 IP 在真实部署拓扑下对不对"。

这也是为什么安全架构师串讲那一环不能省——只有理解业务的人，才知道哪些操作是高风险的、哪些数据是敏感的、哪些提示信息本身就在泄露。

## 五、与其升级工具，不如升级工作流

做完两年排查之后，我对 AI 的态度不是"能不能替代人"，而是"把 AI 放对位置"。

### 三层盲区，三个解法

| 盲区 | 特征 | 工具/AI | 人 |
|------|------|---------|----|
| **知识性盲区** | 规则明确，不依赖上下文 | AI 扫描 + SAST | 人做 triage，去误报 |
| **跨层断裂** | 单层代码无异常，漏洞在交接面 | 当前视角看不到 | 渗透测试（黑盒）+ 业务 owner 结合前后端链路 ​
| **业务逻辑盲区** | 代码语法正确，业务语义危险 | 不懂业务就看不到 | 安全架构师串讲 + 业务 owner 排查 |

AI 的位置在第一行：**用 AI 覆盖知识性盲区，把人的时间省出来，投入到后两行。**

### 跨团队交叉验证的问题

现在这套流程最大的问题不是缺工具，是"谁来做"。三人交叉验证、审自己团队以外的仓——这个设计的假设是：自己不信任自己的代码，所以换一拨人来审。

但两年的经验告诉我，交叉验证在跨层断裂和业务逻辑盲区面前基本无效。一个不熟悉业务的外来 Reviewer 看代码，只能发现第一类问题（知识性盲区）——而这类问题正是 AI 最擅长覆盖的。后两类问题需要的不只是读懂代码，还需要知道：这条调用链上的安全契约是怎么约定的、权限边界画在哪、异常处理在不同层级各有什么约定。**这些上下文 AI 拿不到，跨团队的 Reviewer 也拿不到。**

安全排查真正需要的是"理解"，不是"不信任"。

### 理想的工作流

**白盒排查和渗透测试各司其职。** 不是谁替谁——是三层盲区对应不同的排查方式，分别交给最擅长的一方。

具体步骤：

1. **AI 第一遍扫描**。把所有新增代码喂给 AI，按照 checklist 逐项过——加密算法、正则安全、日志脱敏、证书校验。这些是 AI 的强项，漏不了几个。

2. **人做 triage**。AI 扫出来的东西不会 100% 准确。但 triage 的工作量远小于全量 review。你不需要一行一行看代码，只需要对 AI 标出来的点逐个确认。这个"第一步 AI + 第二步人"的模式，我在上一篇文章里详细写过，在安全排查场景下同样适用。

3. **渗透测试覆盖跨层断裂**。第二类盲区——XSS、SQL 注入、入参校验缺失——这些漏洞在黑盒视角下暴露得最快。安全团队用 Postman 绕过前端直接调 API，天然就是在测"前后端之间的缝隙"。这篇文章里三个影响最大的跨层漏洞，全是渗透测试发现的，不是白盒 review 发现的。这不是说白盒 review 没用——而是说对于跨层断裂，黑盒比白盒更适合做首选检测手段。

4. **业务 owner 主导业务逻辑白盒排查**。第三类盲区——横向越权、纵向越权、审计日志缺失——这些需要从代码层面逐层追到 SQL 才能确认。业务 owner 最清楚自己的鉴权模式、权限边界和异常处理约定。由业务 owner 拿起 checklist，从 Controller 一路追到 Repository，逐段确认"domainID 有没有比对""审计注解有没有加""六要素全不全"。安全架构师标出高风险业务后，集中排查期重点复查。

5. **安全架构师串讲高风险业务**。这是现有流程里最不能被替代的一环。从攻击者视角倒推哪些业务是高风险目标——堡垒机存密码、Runbook 允许执行脚本、自定义文本框可能 XSS——这些判断依赖安全经验，不是读懂代码就能做到的。

### 让 AI 更懂你的仓库：把规则沉淀到代码里

上面跑通之后，还有一个事值得做：**把每次排查发现的仓库特有规则，写进代码仓里。**

两年排查下来，每个仓库都积累了一批特有的坑——哪个仓库的审计日志走 AOP 注解、哪个仓库的 domainID 校验在 Service 层不在 SQL 层、哪个仓库用 MyBatis 且业务需要动态表名只能用 `${}` 但入参必须走枚举。这些知识目前在人脑子里。排查完写一份报告，报告归档，明年排查的人换了，同样的坑再踩一遍。

但如果每次排查结束后，把仓库特化的规则沉淀到代码仓的一个文件里（比如 `CLAUDE.md` 或 `SECURITY.md`），列出：

- 这个仓库的鉴权模式——domainID 校验在 Service 层，不在 SQL 层
- 这个仓库的审计日志方式——AOP 注解 vs 手动上报，新增接口必须加 `@AuditLog`
- 这个仓库的禁止写法——`${}` 允许用但入参必须是枚举，不能直接拼用户输入
- 这个仓库必须检查的点——所有 Controller 方法是否标注审计注解、所有查询是否比对了 domainID

下次 AI 扫描时，加载这个文件，它就不再是"读一遍通用安全规范然后扫"，而是"知道这个仓库的约定然后扫"。从"不要用 MD5"升级为"这个仓库用 AOP 注解做审计，新增接口必须加 `@AuditLog`"。

这仍然只覆盖第一类盲区——知识性盲区。区别在于，知识从"通用安全知识"变成了"这个仓库的安全知识"。跨层断裂和业务逻辑盲区，AI 依然看不到。但至少，你不需要每次排查都把同样的规则重新讲一遍，不需要每次靠人回忆"去年这里出过什么问题"。

### 流程比工具贵，但工具省不掉流程

把 SAST 换成 AI，把手动 grep 换成 Claude Code——这些能让你每年那一个月的排查效率翻倍。但如果第三类盲区的排查流程不存在（没有业务 owner 参与、没有安全架构师串讲、没有跨层联合 review），AI 只是帮你更快地到达"扫完了，没发现什么问题"这个结论而已。

两年排查做下来，最深的感受不是"安全漏洞太多了"，而是**安全漏洞分三类，只有第一类能靠升级工具解决。另外两类，一直在你的盲区里，跟你用的工具好不好没关系。**

## 六、行万里路

最后想说一点和工具、流程都没关系的事。

做了两年安全排查，我肯定比不上专业渗透测试的同学。但这件事情对我作为开发的提升，比读任何安全规范都大。

规范告诉你"要做输入校验"。排查让你看到不做的真实后果——一个 SaaS 平台上的工单，因为 WHERE 条件少了一个 `domain_id`，任何租户都能看到别人的数据。读完规范你不会在写 SQL 时下意识加一句 `AND domain_id = ?`，排查完几十个接口之后你会的。

排查别人的代码，等于提前踩了自己的坑。看到新增接口没有注解导致审计日志缺失，你回头看自己代码，会条件反射地检查每一个 Controller 方法上有没有那一行注解。不是在 checklist 上勾掉一项，是在写代码的时候脑子里自动多了一道工序。

两年下来最大的变化是：**安全从"安全团队的事"变成了"设计的一部分"**。这东西工具教不会你，AI 也教不会你。读万卷书（OWASP、安全编码规范）给你方向，行万里路（实际排查几十个服务、上百条漏洞）给你本能。

而本能这东西，在你写代码的时候是不需要思考的。
