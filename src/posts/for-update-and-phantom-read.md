# FOR UPDATE 在分布式下真的安全吗？

> 一个编排引擎的节点流控实战：为什么 FOR UPDATE 在 PostgreSQL 兼容数据库上也能防并发，以及"设计正确"比"依赖数据库特性"更可靠。

---

## 1. 问题：多个调度实例同时展开循环节点，怎么不超限？

编排引擎的调度层有多台实例。它们的职责之一是把用户定义的循环节点展开成实际执行节点。展开过程是：查询当前这个 execution 下已有多少个节点 → 如果没超限 → 插入新展开的节点。

"查询 + 插入"是两个独立操作。两个调度实例同时查询到当前 299 个节点（限制 300），都判断还没超限，各自插入一个——最终 301 个，超限。

这就是幻读：第一次查询时不存在的行，在事务提交前被另一个事务插入了。

---

## 2. 直觉方案：SELECT ... FOR UPDATE

给查询加排他锁是标准解法：

```sql
SELECT COUNT(*) FROM nodes WHERE execution_id = X FOR UPDATE;
```

其他事务的 FOR UPDATE 会被阻塞，等第一个事务提交后才能读到最新数据。MySQL InnoDB 在 REPEATABLE READ 下还有 Next-Key Lock（行锁 + 间隙锁），物理上阻止了幻读。

但 PostgreSQL 兼容数据库在默认隔离级别下只有行锁，没有间隙锁。理论上两个事务可以同时读到 299、同时插入 300——和没加锁一样。

那为什么我们的方案上线后 0 超限事故？

---

## 3. 关键不在数据库，在业务流程

答案藏在节点入库的时序里。一个 execution 的生命周期有两个阶段：

```
阶段 1：模板解析
  用户提交编排模板 → 调度层解析 YAML → 将所有节点先入库
  （包括常规节点和尚未展开的循环节点）

阶段 2：循环展开
  调度层读取循环节点 → 展开成执行节点 → FOR UPDATE 查询已有数量
  → 判断是否超限 → 插入新节点
```

循环展开发生在模板解析之后。当 FOR UPDATE 执行时，execution 下已经有阶段 1 入库的数据行。`SELECT ... FOR UPDATE WHERE execution_id = X` 一定能命中行，FOR UPDATE 锁住了它们。另一个调度实例的 FOR UPDATE 尝试锁同一批行时，被阻塞等待。

行锁就够了。间隙锁根本不需要。

**方案正确，不是因为数据库帮了忙，而是因为业务流程保证了"必然有行可锁"。**

---

## 4. 如果入库顺序反过来呢？

假设未来架构调整，循环展开被提前到模板解析之前——此时 execution 下 0 行，没有行可锁，两个事务都不会被阻塞。幻读发生。

这不是说 FOR UPDATE 方案脆弱。而是说理解**方案有效的前提条件**比记住"FOR UPDATE 能防幻读"更有价值。

如果真的出现这个场景，标准做法是锁父记录：

```sql
SELECT * FROM executions WHERE id = X FOR UPDATE;
```

锁住 `executions` 表里这一行，串行化所有节点插入。不依赖行数 > 0，在所有支持行锁的数据库上都能工作。

---

## 5. MySQL 下会更"安全"吗？

会，但原因和我们这条线无关。MySQL InnoDB 的 Next-Key Lock 即使 execution 下 0 行也能通过间隙锁阻止并发插入。

但结论不变：依赖数据库特性，换一个数据库就可能失效；依赖自己对业务流程的理解，换什么数据库都能讲清楚为什么对、什么条件下会失效、怎么兜底。前者是记忆，后者是设计。

---

## 6. 总结

这个方案没什么花哨技术——就是 SELECT ... FOR UPDATE。真正有意思的是这个事实：**因为我们控制了入库顺序，所以行锁就够了。** 分布式系统里，业务时序的理解往往比数据库特性更可靠——特性会因版本、厂商而变，但"解析先入库、展开后插新"这个顺序是自己设计的。
