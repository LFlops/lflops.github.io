# Redis 弱密码零停机轮转：一个被你忽略的连接行为

> 改 Redis 密码，微服务会瞬间全部断开吗？不会——因为 AUTH 只在连接建立时生效。利用这个行为，我们设计了一套零停机凭据轮转方案。

---

## 1. 问题：事故驱动的全量排查

事情不是我们自己发现的。

另一个云服务将明文密码写在了对外发布的资料中，被黑客利用，发生了现网安全事故。安全负责人随即要求所有服务排查生产环境中的各类密码。我们对主干配置进行解密和分析，发现了 Redis 使用了弱密码——服务名加简单数字，多个 Region 一致，被内部弱密码检测平台判定为不合格。

事故没有发生在我们身上。但排查暴露了我们的隐患。既然发现了，就得修。

---

## 2. 一个被忽略的 Redis 连接行为

修改数据库密码然后重启服务——这是最熟悉不过的操作。但 Redis 有一个不太被注意的行为，让这件事可以做得更优雅。

Redis 的 `AUTH` 认证只在客户端**建立连接时**验证。连接建立后，即使服务器侧的密码被修改（`CONFIG SET requirepass newpassword`），已经建立的连接**不会被主动断开**。因为 Redis 不会对已认证的连接重新验证身份——连接本身就是"已认证"的凭证。

这意味着：**先改服务器密码，再改客户端配置，中间存在一个"旧连接继续工作、新连接使用新密码"的安全过渡期。**

---

## 3. 方案：利用这个行为实现零停机

基于这个行为，方案变得很简单：

1. **Redis 侧改密码**——通过内部管理平台的前端页面操作，平台自动完成密码下发给各节点并持久化。已有连接不受影响，微服务正常运行。
2. **修改微服务主干配置中的 Redis 密码**。
3. **按 Region 逐个滚动部署**——单 Region 约 15 分钟，工步自动化（下线→停止→卸载→安装→启动→上线），逐台完成。新进程读取新密码建立新连接。
4. **全部部署完成后，旧连接自然消亡**。

整个过程没有停机窗口。每个微服务的重启以分钟计，滚动完成。对于 Redis 的调用方来说，请求从未中断。

**回滚也安全。** 每 Region 至少保留一台机器尚未部署，另一 Region 作为完整容灾。如果过程出现问题，先回滚 Redis 密码，再回滚微服务配置重新部署即可。

---

## 4. 一个集群、多个服务、一次谈判

事情没有"改密码 → 部署 → 完成"这么简单。

这个 Redis 集群不是我方独占的——还有其他云服务共用。改密码意味着他们也得同步更新配置。摆在我们面前两条路：

**方案 A：自己申请新 Redis 集群，完成数据割接后搬走。** 测试环境验证时发现，旧集群数据量太大，内部数据同步平台无法支持完整同步。这条路走不通。

**方案 B：Redis 在 CMDB 上归属我方。其他服务要么配合我们一起变更，要么自行搬走。** 我们选择了这条路——拉着各服务 SRE 评估风险，风险不大的服务纷纷搬离。最终只剩下一个服务，由同一位 SRE 负责运维，在统一变更窗口中完成了同步改密。

CMDB 归属在这里不是形式——它给了我们谈判的筹码。但真正让这条路可行的，是数据同步平台撑不住旧集群的数据量这个客观约束。**约束又一次帮我们做了决策。**

---

## 5. 工程现实：六个月的等待

从发现弱密码到完成轮转，技术方案的执行时间以小时计。但从方案提出到落地，等了六个月。

原因不复杂——三节保障、重大活动保障期间，现网进入熔断状态，禁止一切非紧急变更。弱密码虽然是隐患，但在"没有正在发生的攻击"的前提下，优先级排不到熔断窗口之上。

我们做了能力范围内能做的事：在测试环境验证完整流程，编写 SOP 并通过评审，把方案交到 SRE 手上。三个月后，SRE 在现网执行。过程平稳，零客户端库"惊喜"。

这六个月的等待本身也是运维的一部分——**技术方案可以 15 分钟跑完，但企业运维的节奏不由技术决定。**

---

## 6. 总结

这个方案不靠任何高级技术。靠的是理解 Redis 的一个行为——`AUTH` 只在连接建立时生效——然后利用这个行为设计出零停机路径。

后半段的故事也值得记住：技术决策被数据同步平台的承载能力约束，被 CMDB 归属影响，被熔断窗口拉长到六个月。真实的企业运维，技术方案只是拼图的一块。
