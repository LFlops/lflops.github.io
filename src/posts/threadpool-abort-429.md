# 线程池调优：当 abort 遇到 429

> 队列满了就扩队列，429 多了就调限流——这是直觉。但两个问题之间有一个反馈回路，拆开修只会让事情更糟。

---

## 1. 场景：一个异步任务的日常

一个测试环境的接口调不通了。报错是任务提交后被 abort，偶尔还夹杂着下游 API 返回的 429 Too Many Requests。一开始以为是偶发的，后来频率越来越高，每次压测都炸。

这个接口的逻辑不复杂：用户提交一个异步任务 → API 返回任务 ID → 前端轮询任务 ID 查结果。后台通过线程池把任务提交到下游平台执行，也轮询下游获取结果，最终刷新数据库。任务的平均执行时间约 10 分钟。

线程池的队列大小是 50。这个数字不是我定的——前人留下的，人已经不在了，没有文档交代为什么是 50。

---

## 2. 症状：两个问题同时出现

观察到的现象是两个：

- **abort**：新任务提交后被线程池拒绝，直接报错。队列满的时候新任务进不去。
- **429**：下游 API 频繁返回 429 Too Many Requests。轮询下游结果时，大量请求撞上了下游的限流配额。

直觉上这是两个独立问题——"队列太小了"和"下游限流太紧了"。先扩队列试试？abort 果然变少了。但 429 反而更多了。

这说明不是独立问题。

---

## 3. 根因：两个问题之间的反馈回路

翻日志的时候，abort 和 429 的时间线高度重合。走读了一遍代码逻辑，才发现它们是怎么连起来的。

问题的核心在一个细节：任务一旦提交到下游平台，后台线程就**立即开始轮询结果**——没有间隔，没有退避。这意味着：

- 旧任务在轮询下游获取结果
- 新任务提交后也立即开始轮询
- 新旧任务的轮询请求**抢占同一份下游 API 的限流配额**
- 限流配额耗光 → 所有轮询都返回 429

旧任务因为 429 拿不到结果，无法标记完成，滞留在队列中。队列被旧任务占满，新任务被 abort。调用方收到 abort 后重试，提交更多任务——更多轮询涌入——更多 429。

这是一个正反馈回路：

```
队列满 → 新任务 abort → 调用方重试 → 更多任务入队
    ↑                                      ↓
旧任务滞留 ← 拿不到结果 ← 429 ← 新旧轮询抢占限流
```

每个环节单独看都合理——队列 50 不是不合理的数字，10 分钟的任务也不是特别长，轮询下游结果是必须的，下游有限流也很正常。但它们组合起来，形成了一个自我强化的死亡螺旋。

**扩队列为什么让 429 变多？** 因为更少的 abort 意味着更多任务成功进入了执行状态，全都开始轮询下游——更多的并发轮询请求，更激烈的限流抢占。

---

## 4. 方案：切断回路，不是只扩队列

要打破这个循环，不能只修 abort 或只修 429——要**切断它们之间的连接**。

**扩队列**是必要的。50 对于执行时间 10 分钟的任务来说确实偏小，扩容让任务有更多空间等待执行。但这只是缓解了 abort，没有解决 429。

**新任务延迟轮询**才是切断回路的关键。新任务提交后，不立即轮询结果，而是等待 60 秒。这 60 秒让旧任务先拿到结果、先完成、先退出队列。旧任务消亡了，队列自然空出来，新任务也不需要和旧任务争抢限流。

60 秒是怎么定的？按任务平均执行时间 10 分钟来估算，旧任务在 60 秒内大概率已经接近完成——给它一段不受打扰的时间去拿结果。不是精确调优，是基于经验值加测试验证。另外还有 30 分钟的轮询最大超时作为兜底——如果一个任务 30 分钟还没拿到结果，放弃。

**效果：** 调优前，测试环境接口频繁报错，压测无法正常完成。调优后，接口恢复正常响应，不再出现任务中断，吞吐量提升约 2 倍。没有精确的 P99 对比数据——因为调优前接口频繁中断，根本没有稳定的 P99 可测。

---

## 5. 复盘：修完不是终点

**"前人的 50"**——接手一组不合理的默认值是运维的日常。这个 50 在低负载时完全够用，一旦并发上来就炸。不是谁的错，是没有人知道"多少才够"。

**告警的两个盲区：** 有网关日志告警（500/400 触发），有业务指标告警（通过 SDK 上报指标平台清洗后触发）。但**没有队列深度告警**——修完之后也没有加。这是一个诚实的盲区：修好了症状，没有预防下一次类似的排队问题。

**根因不在单个组件。** 队列满不是问题，429 也不是问题——它们各自在正常范围内。问题是它们之间的交互形成了一个反馈回路。复合故障的根因分析，看的不只是每个组件有没有问题，是它们组合起来之后发生了什么。

---

## 6. 总结

这个方案不复杂——扩队列加延迟轮询。但如果不是先搞清楚 abort 和 429 之间的关系，单纯的"扩队列"只会让 429 更严重，然后下一个接手的人可能会去调下游限流，然后发现 abort 又回来了。

修 bug 之前先理解 bug 之间的连线。有时候，bug 之间是朋友。
