# 一次 VNC 提权漏洞的完整生命周期：从应急到源头治理

> 蓝军通过其他云服务的漏洞拿到了我们 ECS 的 VNC 链接。CVSS 三项全 HIGH。以下是完整的应急、排查、治理和复盘过程。

---

## 1. 发现：一封邮件

邮件是直接发给安全接口人的。蓝军通过其他云服务的越权漏洞提权，拿到了我们服务生产环境 ECS 的 VNC 链接。机密性、完整性、可用性三项全打了 HIGH。

收到邮件的时候，我对 VNC 的认识和大多数开发一样——"页面版的 SSH"。关掉浏览器窗口不就退出了吗？为什么会残留会话？

先处理事，再搞清楚为什么。

---

## 2. 应急：当天

高危漏洞有 SLO 压力。CVSS 评分决定了响应时间——评分越高，给你的窗口越短。这个是大家的 KPI，不存在"先放一放"。

第一步，拉临时会议作为非正式的 warroom。整理要处理的事项、分派责任人、标记时间节点。然后把对应的人拉上会，统一宣发。最后发邮件抄送领导，作为会议纪要和时间承诺。

接下来是硬骨头——拉通**全部**微服务团队，逐一排查各自 VNC 链接内是否存在未退出的 SSH 会话。

问题是：你怎么知道"全部团队"是哪些？你怎么确认每个团队真的查了而不是回复"已排查无问题"？

我们的做法：把所有环境和机器的列表拉下来做成在线表格。按业务方分配排查责任人。提交公共变更单——多个执行人 + 多个配合人，一人操作一人复核。每个团队的排查结果回填表格，有据可查。

四级审批链——开发 → 团队负责人 → 服务负责人 → 部长——加上 SOP 需安全负责人、架构师、服务负责人三方评审。但高危漏洞的 SLO 压力下，审批链跑得比平时快得多。因为漏洞单挂了所有人的名字。

**当日闭环。**

---

## 3. 排查：为什么 VNC ≠ SSH

应急处理完之后，我开始搞清楚最根本的问题——为什么 VNC 会有这个行为？

拉了 ECS 的安全负责人对齐。情况是这样的：

VNC 本质上是一个**视频流**，底层的连接协议是 SSH。当你通过 VNC 登录到 ECS 后，系统启动了一个 SSH 会话。但当你关闭 VNC 浏览器的标签页——

- **你以为**：退出 VNC → 退出 SSH → 会话结束
- **实际上**：退出 VNC 只是断开了视频流，SSH 会话还在。下次打开 VNC 链接，画面重新连接，你直接进入上次的登录状态

ECS 还提供了页面版的 SSH 通道。但生产环境的 ECS 没有 EIP 也没有 NAT，无法直接通过本地 Xshell 访问。运维人员习惯上优先使用 VNC——所以这个通道被反复使用，而没有人意识到它的"断开不等于退出"特性。

更麻烦的是，一位同事之前的运维操作中，直接以 root 登录后没有退出。下次 VNC 打开，root 权限直接暴露。一台机器上残留了 root 会话。

**VNC 是视频流，不是文本流。** 这意味着——CLI 脚本扫不了它。接口请求查不了它。没有任何自动化手段能判断"这个 VNC 会话里有没有人还登着"。排查只能靠人——一台一台进去看。

这就是为什么之前的年度安全合规排查没发现这个问题——不是漏了，是 VNC 这个通道根本不在脚本和接口的扫描范围之内。

---

## 4. 治理：三部落地的防御，和一条没走通的路

应急是堵住当前的漏洞。治理是让它不再发生。

**第一层：配置。TMOUT 会话超时。**

写了一个 shell 脚本。逻辑不复杂：先检查当前环境变量里是否已有 TMOUT → 再检查 /etc/profile 里是否已有配置 → 都没有则在 /etc/profile 追加 `export TMOUT=900` 并执行 source。保证幂等——已配置的机器不会被重复添加。

在测试环境验证了所有现网类型的镜像，确认脚本不会破坏已有配置。

**第二层：流程。SOP + Runbook + 运维规范。**

SOP 需要安全负责人、架构师、服务负责人三方评审。评审通过后通过 Runbook 全量部署到全部 400+ 台生产主机。同步更新运维规范，明确要求：**先退出 SSH 会话，再关闭 VNC 页面。**

**第三层：权限。从 IAM 层面禁止 VNC。**

云平台的变更提权机制是 IAM 预制用户组——变更人员通过变更单提权，系统创建临时用户并加入高权限用户组，获得临时的操作权限。我们在高权限组中明确添加了 **DENY VNC Action**。

这意味着：即使运维人员通过变更单提权，也无法创建 VNC 链接。无法创建，就无从泄露。

万一需要紧急使用 VNC？走事件单或紧急变更单申请恢复权限，审批人是服务负责人 + SRE 代表。这个禁用只影响我们服务的 ECS 资源，不影响其他服务。

从提出到落地，走的是标准变更流程——测试环境验证 → SOP → 变更单 → 夜间执行。安全治理不需要特殊权限和紧急通道。它应该是日常运维的一部分。

**一条没走通的路：镜像层加固。**

最初的设想是推动操作系统镜像方提供等保加固镜像——从镜像层面内置 TMOUT 和 VNC 使用规范。但对方不支持。

后来在容器平台申请新节点的页面上发现了等保加固的选项，勾上之后新节点会自动带上安全配置。但这个选项对已有节点无效——现网 400+ 台机器不会因为你勾了一个选项就自动更新。

这条路的尽头是：**新节点可以走等保加固，已有节点靠 TMOUT 脚本单点覆盖。** 不是完美的方案，但在当时的约束下，是能做到的最好。

剩下的长尾问题是——TMOUT 加固是一次性 Runbook 部署。如果后来人新建了机器、重建了镜像、或者交接时忘了这一茬，防御就有缺口。最底层的兜底是 IAM VNC 禁用，但这个禁用也可能被后来人启用。运维交接的长尾问题，没有一劳永逸的方案。

---

## 5. 复盘

**应急靠流程，不是靠个人英雄。** 高危漏洞 → CVSS 评分 → SLO 驱动的响应窗口 → warroom 分工 + 时间节点 → 邮件抄送领导 → 审批链加速——每个环节都依赖流程存在，而不是某个人的判断。

**根源治理靠层层递进。** 单点修复只是第一层。第二层是流程（SOP + 规范）。第三层是权限（IAM DENY）。每一层是上一层的兜底，但每一层都有自己的盲区——所以需要层层叠加，而不是追求一层完美。

**安全是把"为什么可以发生"的每个环节都堵上。** VNC 不等于 SSH——这个认知盲区才是根因。修完漏洞之后，把 VNC 会话排查纳入了例行安全审计的 checklist，把 VNC 使用规范写入了运维 SOP，把 VNC 权限在 IAM 层面禁掉。不是修了一个漏洞，是消灭了一整类风险。

---

**还没做的事：**

- **其他逃生通道**：串口控制台？IPMI？当时聚焦 VNC 闭环，没有扩展到其他类似机制。这是一个诚实的盲区。
- **TMOUT 的持续覆盖**：新机器、重建镜像的机器，需要依赖后续的 SOP 执行或容器平台的等保选项。没有做成自动化的持续检测。
- **蓝军的完整攻击链**：原始漏洞在其他云服务侧，详情未传递给我方。这个问题上，我们只看到了暴露面，没看到完整的攻击路径。
